Executive Summary
WeePay is WeeFly’s payment orchestration layer between the booking and instalment engines and external payment providers. It does not process payments directly; it selects providers, normalizes provider responses, records transaction state, and coordinates webhook-driven updates.
The Layer A design is modular and provider-agnostic. It defines adapters, corridor-based routing, versioned coverage configuration, transaction state control, idempotency, monitoring, security controls, deployment, rollback, and operating procedures. Layer B—treasury, cross-border settlement, Ecobank orchestration, and FX—is explicitly deferred.
Production-readiness position
The source is marked “Production Draft.” Stripe is specified in detail, while Katamy Pay and InstaPay retain production-blocking open questions. SISP/Vinti4, Revolut, and Pix remain adapter stubs. Circuit breaker implementation, security testing, PCI scope validation, and performance work are also outstanding.

1. Architecture Overview
1.1 What is WeePay?
WeePay is WeeFly’s payment orchestration layer. It sits between WeeFly’s booking/instalment engines and external payment providers. It is not a payment processor itself—it routes, normalizes, and tracks payments across multiple providers.

1.2 Design Principles
Table 1. Design principles

4. Core Concepts
4.1 Corridor
A corridor is a country + payment_method combination. It is the fundamental routing unit.
corridor = f"{country}-{method}"  # e.g., "CV-card", "NG-mobile_money", "BR-pix"
4.2 Provider Slot
Providers occupy slots, not fixed roles:
Primary slot: First-choice provider for a corridor.
Fallback slot: Used on coverage gaps or outages.
The same provider can be primary in one corridor and fallback in another.

The result of initiate()—what the customer uses to complete payment:

7. Routing Engine
7.1 Algorithm
def route(corridor, amount, currency):
    config = load_coverage_config(corridor)
    if not config.primary_provider:
        return fallback_immediately("NO_PRIMARY_DEFINED")
    primary = config.primary_provider
    # 1. Coverage gap check (permanent)
    if not primary.covers(corridor):
        return fallback("COVERAGE_GAP", retry=False, alert=False)
    # 2. Amount limits
    if amount outside [min, max]:
        return fallback("AMOUNT_OUT_OF_RANGE", retry=False)
    # 3. Health check
    health = check_health(primary)
    if health == DEGRADED:
        return primary_with_fallback("PRIMARY_DEGRADED", timeout=5s)
    if health == DOWN:
        return fallback("OUTAGE", retry=True, max_retries=1, alert=True)
    # 4. Primary is healthy
    return primary("PRIMARY_AVAILABLE", retry=True, max_retries=2)

1. Load corridor coverage configuration
↓
2. If no primary is defined, fail over immediately
↓
3. Check permanent coverage gap
↓
4. Validate amount limits
↓
5. Check primary-provider health
↓
6. Route to primary, primary-with-fallback, or fallback according to health

8.2 Terminal States
Terminal states
COMPLETED, FAILED, CANCELLED, EXPIRED, REFUNDED, PARTIALLY_REFUNDED. Terminal states are immutable except DISPUTED can be reached from COMPLETED.
8.3 Transition Rules
Idempotency: duplicate (transaction_id, event_id, provider) ignored.
Webhook precedence: webhook wins over status check on conflict; log the discrepancy.
Timeouts: PENDING → EXPIRED after instrument expires_at; PENDING → FAILED after 24h (configurable); AUTHORIZED → FAILED after 7 days (configurable).

@pytest.mark.asyncio
async def test_initiate_card_declined(adapter, sample_params):
    from stripe.error import CardError
    error = CardError(
        message="Declined",
        param="",
        code="card_declined",
        decline_code="insufficient_funds",
        http_status=402,
    )
    with patch("stripe.PaymentIntent.create", side_effect=error):
        with pytest.raises(ProviderError) as exc:
            await adapter.initiate(sample_params)
    assert exc.value.code == ProviderErrorCode.INSUFFICIENT_FUNDS
    assert exc.value.retryable is False
